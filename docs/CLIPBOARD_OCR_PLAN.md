## 目标

让剪贴板里的图片内容可被文字搜索命中，并且跨设备可搜：在 A 复制一张含文字的截图，B 的剪贴板搜索框或“文本”智能分组里输入图中文字即可搜到这一条，并在 B 上按需查看/复制原图。识别在本机完成；同步只发生在已配对的可信设备之间，不写日志。

## 平台能力

- macOS：Vision `VNRecognizeTextRequest`（macOS 10.15+）。支持 `recognitionLanguages`（如 `["zh-Hans", "en-US"]`）与 `recognitionLevel`（`.fast` / `.accurate`），纯本地推理，无需网络和额外权限。
- Windows（后续）：`Windows.Media.Ocr.OcrEngine`，同样本地。
- 不建议引入第三方模型；若将来要更强中文识别，再评估系统之外的可选模型。

## 架构选择

Rust 引擎持有数据与搜索，但 OCR 属于平台能力。推荐：

1. **Swift 客户端跑 OCR，Rust 只存结果**（推荐）
   - 新增引擎列 `ocr_text TEXT`、`ocr_lang TEXT`、`ocr_version INTEGER`，增量迁移（沿用 `title` 列的做法）。
   - 新增 `set_item_ocr` 操作写入识别结果；查询把 `ocr_text` 纳入自由搜索与“文本”规则。
   - Windows 端未来用 `Windows.Media.Ocr` 写同一个操作，引擎保持跨平台。
2. 备选：Rust 侧通过 `objc2` 直接调 Vision。省一次回写，但把引擎绑到 macOS，且 Windows 要另写一套，不推荐。

## 触发与调度

- 记录入库（`ingest`）后，如果 `kind == image`，把记录加入 OCR 队列。
- 只处理本地已有字节的图片（`imagePng` 或本地图片文件）；纯远端索引先跳过，等正文按需取回或用户复制后再排队。
- 逐条识别，不做任何基于 OCR 内容的去重或合并：每条图片记录各自得到自己的识别结果，即使多张图识别出相同文字也互不影响。
- 仅做“同一条记录不重复识别”的幂等缓存（键为 record id + `blob_hash` + `ocr_version`），避免同一记录反复入队时浪费算力；这是任务去重，不是记录去重，也不会修改历史行。
- 后台低优先级：并发 1–2、单图最长边先降到 1600 px、单张超时（如 3 秒）放弃；面板打开或前台忙碌时暂停。
- 缩略图与 OCR 分开：缩略图用于展示，OCR 用较大的图，避免小图漏字。

## 存储与检索

- `ocr_text` 只存识别文字（小写化用于匹配），与 `search_text`、`title` 一起参与自由搜索。
- **OCR 文字只用于搜索索引，不参与历史记录去重、合并或列表成员判定**；记录去重仍然只由现有剪贴板内容摘要（`cl_items.digest`）决定，与 OCR 无关。
- 智能列表的“文本”条件同时匹配 `search_text`、`title`、`ocr_text`；可按需增加“图片文字”单独条件。
- 识别文字随记录按保留期清理，删除记录即删除；被排除 App 的记录不落库，因此也不会 OCR。
- OCR 文字与图片正文会作为搜索索引在已配对设备之间同步（见下节）。

## 跨设备同步与检索

现有实时剪贴板同步只覆盖“两端在线时的新复制”，且普通历史不会因重连整体补发。要让 B 搜到 A 历史里有、但当时未同步的图片，需要一层可检索的索引同步。原则是**同步索引、按需取正文**：

### 同步内容

- 索引记录（体积很小，每条几 KB）：新增 `index:` 记录类型，键 `index:{global_id}`，值包含
  `global_id / digest / kind / mime / length / preview / source_device_id / source_app_id / source_app_name / copied_at_ms / title / ocr_text / ocr_lang / ocr_version / blob_hash / blob_size`。
- 正文（编码后的剪贴板快照，含 PNG）**不随索引推送**，由对端在需要时按 `blob_hash` 拉取。
- 复用现有同步基础：`cl_operations` 的操作日志 / 因果版本 / 墓碑、`cl_blobs` 的内容寻址与分块校验、`library_files` 的按需获取通道。只在已配对且可信连接的设备间传输，不经过公网服务。

### 远端索引行

- 收到索引后落一条“远端索引行”（`ordinary=2` 或 `remote_only=1`）：参与自由搜索与智能分组，但本地没有 `payload`。
- 与本地已有同 `digest`/`global_id` 的行合并，避免重复展示；同一内容在多设备复制时按 `global_id` 归并，不因 OCR 文字相同合并。
- 时间戳沿用原始 `copied_at_ms`，不回写成接收时间。

### 按需取正文

- 选中/预览/复制远端索引行时，按 `blob_hash` 向来源设备或任一持有该 blob 的在线设备拉取；分块传输 + SHA-256 校验，完成后写 `cl_blobs` 并把该行补成本地可用，后续正常复制/暂存。
- 可选：为搜索结果预取小缩略图（长边 160 px）以便展示；正文仍按需。
- 来源离线或 blob 已清理时，保留索引的文字搜索能力，正文状态标“使用时获取/暂不可用”（沿用现有文件项的 `canRequestFiles` 状态机）。

### 检索行为

- 搜索同时命中本地行与远端索引行；命中来自远端 OCR 时在结果上标出来源设备与“图片文字”。
- 智能列表“文本”条件对两类行一致生效；分页与总数合并统计。

### 存储、配额与保留

- 索引按本机保留期保存，随记录删除并写墓碑，远端随之移除。
- 正文沿用现有传输缓存配额与清理策略；正在预览/复制/暂存的获取任务受保护。
- 索引同步始终开启；用户可选择清除已同步的远端索引，不影响本机搜索已有结果。

## UI

- 搜索本身不需要新界面。
- 图片预览里加一段可折叠的“识别文字”，支持选中复制；没有识别结果时不显示。
- 远端索引行标“来自 <设备> · 使用时获取”，正文到达前显示占位与索引信息（标题、识别文字、预览）。
- 搜索命中来自 `ocr_text` 时给一个“图片文字”小标记，避免用户困惑“图里没有可见文字却命中了”。

## 成本与风险

- 性能：Vision 单张截图通常几十到几百毫秒；批量历史图片首次索引会比较重，需要限流与分批。
- 网络：只看索引时带宽很小；正文按需拉取，受现有传输缓存配额约束。大图首次跨设备查看需要等待。
- 准确率：截图类中英混排表现尚可，手写、小字号、艺术字会漏；只作为“可搜到”的辅助，不承诺完整。
- 隐私：图片正文与识别文字可能包含敏感信息，只能在可信设备间同步；提供开关；索引与日志分离，诊断只记计数与状态，不记录识别正文。
- 版本：不同 macOS 的 OCR 质量有差异，`ocr_version` 用于必要时重跑或以本地结果覆盖远端索引里的旧结果。

## 里程碑建议

1. 引擎：`ocr_text` 列 + `set_item_ocr` + 搜索/智能列表接入（可先只存不识别，便于联调）。
2. Swift：Vision 识别器 + 队列 + 按记录幂等，仅处理本地图片。
3. 同步：`index:` 记录类型 + 远端索引行 + 与本地行按 `digest` 合并；查询包含远端索引行。
4. 按需正文：复用 `cl_blobs`/`library_files`，选中时拉取并 materialize；缩略图预取可选。
5. 体验与开关：远端标记、识别文字展示、命中标记、跨设备同步开关与清理入口。
6. Windows：`Windows.Media.Ocr` 与同一索引协议，跨端行为对齐。
