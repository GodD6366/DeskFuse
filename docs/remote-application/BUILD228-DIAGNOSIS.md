# Build 228 双机控制日志分析

输入：用户提供的 `uniDesk-A.jsonl`、`uniDesk-B.jsonl`（2026-09-18）。A 为控制端，B 为被控端。原始文件留在用户共享目录，未复制进源码。

## 已确认的问题

A 日志有 5 次 `receive_controlReady`、3 次 `viewer_pause_lost`。第一次在 A 本机时钟 1789711030184ms 收到控制确认，1789711030802ms 丢失本机暂停状态；另一次 1789711140747ms 确认，1789711140927ms 丢失。对应区间 `healthy=true`，输入计数为零。B 记录了 `configure_waiting_pause`、`armed`，随后收到 A 的释放请求。

`tokio_bridge.rs` 的更新轮询每 2 秒执行，未准备安装更新时仍调用 `resume_after_update()`。旧实现通过 urgent `p` 无条件把共用 AtomicU8 清零，误清除远程应用的 4/5（被控端独占）或 6/7（控制端暂停共享），使跨屏捕获重启。A 再检测到暂停丢失便释放远端控制。

## 修正

- 两条更新恢复路径共用 `resume_update_pause`，原子地只清除更新所属的 1/2/3 状态；不触碰远程应用的 4..7 状态。
- 被控端输入租约检测独占权是否仍然存在，丢失时释放并记录 `exclusive_ownership_lost`。
- 仅在确实配置过输入租约时发送释放消息，避免未控制时每次心跳都刷一条释放日志。
- B 另有一次 `foreground_changed`（1789711113882ms），当时刚完成 arm；不能仅凭现有日志推断具体切换方。新增目标 PID 与实际前台 PID 记录，保留前台切换保护。

两端时钟存在偏差，因此先按各端单调事件顺序、消息往返与会话关联判断，不用裸时间戳推断跨端先后。
