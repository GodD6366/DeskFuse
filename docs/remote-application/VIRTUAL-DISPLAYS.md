# 远程应用专用虚拟屏幕

开启虚拟屏幕模式后，主程序采用「一应用一屏、多路采集、单路输入自动交接」。多个应用可以同时显示并交替操作；不是多个独立 macOS 用户会话，也不承诺多个应用同时接收键盘输入。使用前提是 B 不同时进行本地操作。

## 模式开关

- A 端应用列表及远程窗口的更多菜单提供「虚拟屏幕模式（实验性）」开关，默认关闭，选择保存到本机偏好；两个入口同步，不修改 B 的全局设置。
- 开启时，新会话申请专属虚拟屏幕并迁移窗口；关闭时，不创建虚拟屏幕、不迁移或调整窗口，使用原有应用窗口采集与前台输入保护。普通模式仍有遮挡、共享焦点等限制。
- 修改仅在下次打开或重新连接应用时生效，不打断已打开会话；暂停/恢复、画质调整不会改变当前模式。重新连接会先清理旧会话的屏幕，再按新选择启动。
- 模式由 `.launch` 消息单独传递，不混入实时画质偏好；缺少模式字段的旧消息按普通窗口模式处理。需要更新两端主程序以支持此开关。
- 虚拟模式下的屏幕创建失败或丢失仍明确报错，不会借开关逻辑自动退回物理屏幕。

## 当前实现

- 每个主机应用会话持有一块 1920 × 1080、60 Hz、非 Retina 虚拟屏幕；全局最多 4 块（约 8.3 MP 原生显示预算）。同一进程不能被两个会话重复分配。
- 首个标准窗口通过 Accessibility 移动并铺满屏幕可用区域，不进入 macOS 原生全屏。只迁移可移动的 AXWindow，跳过桌面层及其他辅助功能元素；Finder 没有文件窗口时通过 LaunchServices 打开个人文件夹。其他窗口、AX 可枚举的同进程对话框安置到同一屏幕；监视器继续跟踪新窗口和移出屏幕的窗口，鼠标拖动期间不重排。放置检查以完整屏幕边界为准，不因 Dock/菜单栏改变可用区域而反复移动或报错。应用强制最小尺寸大于屏幕时，只采集屏幕内可见部分。
- 采集明确绑定屏幕 ID，并以整块专属屏幕作为稳定的输入坐标范围；窗口/候选面板范围仅更新显示布局，不因焦点切换重建租约。失焦不会停止媒体会话。显式指定的屏幕找不到时不退回物理屏幕。最小化 A 的远程窗口暂停媒体，但保留 B 的屏幕和窗口位置，恢复时继续使用原屏幕。
- 切换控制先停止旧输入转发，再向签名输入服务发送带新 nonce 的 `quiesce` 屏障；服务清空待处理输入、确认原生 `release_all` 后回传确认，UI 才能激活新应用。超时拒绝切换，旧确认不能满足新请求；不同远端设备不能抢占已有控制。
- 接管握手先等待已在运行的采集配置完成，再阻止新的采集重配置，避免在原生输入授权期间被新画面代次取消。原生释放确认后，通过 AppKit 和 Accessibility 激活目标应用及已迁移的普通窗口，仍须确认前台 PID 才能授权输入。
- 保留前台 PID、授权、心跳、画面代次和序号保护。除周期检查外，输入服务在授权注入及每个输入包处理前检查前台进程。首次点击仍由既有 viewer 握手队列缓冲，画面变更时丢弃而非重放。
- 正常关闭、断连、启动失败、应用退出或采集错误时，停止采集并尝试恢复原窗口位置及最小化状态，再释放屏幕；不退出目标应用。原物理屏幕已移除时把窗口放回现存普通屏幕。快速退出 DeskFuse 时同步尝试恢复，崩溃不承诺恢复原布局。
- 专用屏幕使用固定 vendor/product 标识 `0x4453 / 0x5241`。Rust 显示拓扑根据原生标识排除它们，独立输入服务无需依赖 UI 中的临时屏幕 ID 列表。第三方虚拟屏幕不受此过滤影响。

实现入口：`RemoteApplicationDesktop.swift`、`DeskFuseVirtualDisplay/DFRemoteVirtualDisplay.m`、主程序 `RemoteApplicationSession.swift`、Rust `remote_application_input.rs`。

## 权限与边界

- B 上主程序需要屏幕录制及辅助功能权限；输入仍由已有签名输入服务处理。请更新主程序和输入服务，旧输入服务不会确认新的交接屏障。
- `CGVirtualDisplay` 是未公开 API。桥接在运行时检查类和方法，不硬链接私有类；缺失、创建失败或屏幕失效会明确失败，没有物理屏幕兜底。编译成功不代表所有 macOS 版本、签名和分发渠道都支持它。
- macOS 全屏 Space、不可移动/无法通过 AX 枚举的窗口暂不支持。跨进程文件面板、系统弹窗、Stage Manager、其他 Space 和应用失焦暂停渲染需要逐应用实机验证；不能仅凭虚拟屏幕保证兼容。
- 虚拟屏幕不是隐私隔离边界。Chrome 等浏览器仍使用专属屏幕区域采集，其他应用或系统窗口若出现在该区域也可能被采到；不要把敏感窗口移动到专用屏幕。
- 窗口恢复是尽力执行，失败数量写入 `virtual_display_closed` 诊断；应用拒绝 AX 操作、退出或原屏幕消失时，不能承诺原样还原。
- 暂不动态调整虚拟分辨率，不保证睡眠/唤醒后自动重建屏幕。屏幕失效时关闭该会话并提示重新连接，不影响其他会话。

## 验证

自动测试不创建屏幕、不移动真实窗口、不注入系统输入：

```sh
cargo test --locked -p deskfuse-platform-macos only_deskfuse_application_displays_are_reserved --lib
cargo test --locked -p deskfuse-engine remote_application_input --lib
# 使用完整 Xcode 的工具链
swift test --package-path apps/deskfuse-macos/RemoteApplication --filter 'displayMode|remoteDesktop|inputHandoff|inputLeaseRejectsReplay|stalePresentation'
./scripts/build-native-macos.sh debug
```

两机人工验收（尚不能用编译或单元测试替代）：

1. B 授权后，在 A 开启虚拟屏幕模式，同时打开 Chrome 和 TextEdit。确认两块独立扩展屏，B 的物理屏不被采集；普通屏幕布局、鼠标穿梭列表不出现专用屏幕。
2. 在 A 反复切换两窗口，验证首次点击、键入、中文候选窗、滚动、拖选及按住修饰键切换。不串键、不粘键；未操作的窗口继续出帧。
3. 新建第二文档窗口、弹出同进程对话框、拖动到边缘；拖动期间不重排，释放后回到专用屏幕。检查跨进程文件选择面板的实际兼容性。
4. 最小化/恢复 A 的一个窗口，确认屏幕未回收、另一路采集不中断。关闭再重连，检查原位置/最小化状态恢复且无屏幕泄漏。
5. 打开第 5 个应用、重复控制同一进程、让另一设备抢占、撤销权限、退出目标应用、断开网络、睡眠唤醒或移除屏幕：应有明确失败且不会采集或注入到其他应用。
6. 正常退出 DeskFuse、再启动，确认没有残留专用屏幕；另测强制退出后的系统窗口回迁行为和恢复限制。
7. 关闭开关，确认当前会话保持原模式；重新连接后恢复 B 的原窗口位置、不再创建虚拟屏幕，画面及输入可用。切换画质或最小化/恢复不能改变模式。重启 A 后开关仍保持关闭。

### 短暂窗口枚举缺失（2026-10-04）

已建立采集的虚拟屏幕会话在 AX 可移动窗口列表或 ScreenCaptureKit 应用窗口区域暂时缺失时，最多保留原视频流 3 秒，每 250 ms 重试；第一轮缺失就释放原生输入与控制权，恢复后须重新点击获取控制。持续缺失则结束会话并恢复窗口。首次启动仍遵守原有 30 秒等待窗口的上限。专用屏幕断开、权限错误、不可迁移窗口等非 `noWindow` 错误不进入该宽限路径，且不会回退到物理屏幕。

专用屏幕的采集边界不依赖窗口 crop；窗口区域缺失时不制造可输入区域、不更新旧画面的布局。诊断 `capture_prepare_failed` 含 AX/屏幕检查阶段，`capture_source_failed` 含 SCK 阶段；`capture_window_retry` / `capture_window_timeout` 区分重试与终止。查看端 `receive_error` 记录限长 reason，便于区分主机发出的实际错误。

本机日志只能确认 Finder 曾正常输出画面后收到 `noWindow`；未取得被控端阶段日志前，不能断言是 AX 枚举还是 SCK 枚举触发。以上是对代码中单次枚举缺失直接终止的修复，不代表已完成修复后的双机 Finder 验收。
