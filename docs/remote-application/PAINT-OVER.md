# 静止画面重编码（paint-over）

2026-11-06：远程应用的视频流在画面静止后重新精细编码，避免文字长期停在“运动时的清晰度”。

## 背景

同一条自适应码率同时服务运动和静止画面，而码率是按最坏情况选的：滚动、拖动、动画会把预算花在变化上。画面停下来后没有新内容，编码器仍沿用上一帧运动状态下的粗糙量化，于是用户阅读静态文字时看到的是最后那一帧的清晰度，而不是源画面的清晰度。

voxl（`tembo/voxl`）用 `--paintover-crf / --paintover-burst / --paintover-delay-ms` 做同一件事：静止后按更低的 CRF 重编若干帧。我们只借用这个行为，不引入它的 x264 软编管线（DeskFuse 用 VideoToolbox 硬编）；x264 是 GPL-2.0，链接它的二进制会被传染，而这次没有引入任何第三方代码。

## 行为

- 捕获连续静止 `settleDelay`（默认 180 ms）后，把最后一张已捕获的原始像素再编码 `burst`（默认 3）帧；每帧间隔一个帧周期。
- 重编码期间把 `AverageBitRate` 临时提高 `bitrateMultiplier` 倍（默认 3 倍，上限 200 Mbps）。VideoToolbox 的参考帧是它自己的有损重建，而输入是干净的源像素，因此多出来的比特用于消除量化误差，静止画面逐帧收敛回源画面，然后停止。
- 只要出现新捕获（内容变化），本轮重编码立即结束并交还自适应码率；因此运动中不会额外编码，也不会出现“静止锐化”和真实内容抢码率。
- `cooldown`（默认 1 秒）限制两次重编码的最小间隔，避免在两幅静止画面之间来回切换时每停一次就重编一次。
- 流控窗口已满时不加重编码帧；下一次静止再处理。重编码帧是普通 P 帧，不消耗关键帧，走同一条序号链。
- 指标 `MediaStatistics.paintOverFrames` 记录重编码帧数，用于判断是否真的生效。

## 实现

- `PaintOverPolicy` / `PaintOverPlanner`（`Sources/DeskFuseRemoteApplication/PaintOver.swift`）：纯时序决策，可单测；不接触捕获、编码器或传输。
- `VideoEncoder`：每次 `submit` 按 `settleDelay` 布一次检查，用序号淘汰过期的检查；队列内判断静止、抬高码率、把最后一帧放回 `latest`，与既有的“最新帧覆盖未编码帧”合流；新内容、突发结束、网络采样和 `stop()` 都会归还码率。
- 与既有机制的分工：损伤驱动捕获、单帧覆盖和基于确认的流控在本仓库已有，不属于本次借用范围；voxl 的条纹编码（为浏览器端多解码器分摊）和 `/wait`（给 agent 的静默等待接口）没有对应的 DeskFuse 场景，未实现。

## 验证边界

- 单测覆盖：静止判定、运动中取消、冷却、禁用、码率抬升与上限，以及真实 VideoToolbox 出帧（静止后自动多出 `burst` 帧、没有新捕获不会无限重编、运动时 `paintOverFrames` 保持 0）。无硬件编码器的机器上该用例自动跳过。
- 未验证：双机实机下的静态文字清晰度主观收益、重编码瞬间对自适应码率的干扰程度（单轮 3 帧、窗口满时跳过，理论上只占 1–2 个采样）、以及高码率档位（≥40 Mbps）下是否值得开启。这些需要双设备观察后按档位决定是否关闭。
